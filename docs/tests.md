## Тесты

## Регламент и архитектура тестирования монорепозитория TaskFlow

В данном документе описаны стандарты проектирования, запуска и поддержки
тестовой экосистемы для микросервисов `flow` и `tasks`.

---

### 1. Контуры тестирования и верификация контрактов

Инфраструктура тестов разделена на три независимых контура:

1. **Изолированные тесты роутеров (Контур 1):**
   * Обеспечивают полную изоляцию от операций ввода-вывода (СУБД, Redis, S3).
   * **Назначение:** Верификация контрактов взаимодействия и маппинга схем.
   * Проверка вызовов базового репозитория `BaseCRUD` стандартизирована:
     простые типы проверяются методом `assert_called_once_with()`, а
     динамические словари и типы моделей извлекаются через нативные
     свойства `.args` и `.kwargs`.
2. **Тесты сервисного слоя и фоновых задач (Контур 2):**
   * Проверяют корректность бизнес-логики и SQL-инструкций на реальных СУБД.
3. **Интеграционные тесты (Контур 3):**
   * Эмулируют клиентские HTTP-запросы через асинхронный `AsyncClient`.

---

### 2. Инфраструктурная изоляция окружения

Тестовые базы данных разведены на хост-машине по изолированным портам:
* **Микросервис Flow:** Порт `5435`, файл настроек `.env.flow.test`
* **Микросервис Tasks:** Порт `5436`, файл настроек `.env.tasks.test`

Управление жизненным циклом Docker-контейнеров автоматизировано на уровне
тестового рантайма через системные асинхронные хуки `pytest`:
* `pytest_sessionstart` — инициализирует Postgres и выполняет опрос
  готовности через утилиту `pg_isready` (Healthcheck) для исключения
  состояния гонки.
* `pytest_sessionfinish` — корректно останавливает и зачищает окружение.

---

### 3. Оптимизация сброса состояния базы данных

Вместо повторного выполнения миграций (`DROP/CREATE`) перед каждым тестом
внедрен механизм каскадного сброса таблиц. На основе метаданных SQLAlchemy
(`Base.metadata.sorted_tables`) динамически формируется и выполняется
единая SQL-инструкция:
```sql
TRUNCATE TABLE table1, table2, ... CASCADE;
```
Данный подход позволил сократить общее время выполнения пакета тестов.

---

### 4. Стандарты кодирования и переиспользование кода (DRY)

При разработке тестов применяются следующие технические соглашения:

1. **Инструменты имитации поведения:** В качестве основного инструмента
   используется фикстура `mocker` плагина `pytest-mock`, обеспечивающая
   управление контекстом подмен без изменения сигнатур методов.
2. **Универсальные фабрики:** Для исключения дублирования при сборке сложных
   вложенных структур объектов в `conftest.py` (`ZONE 6`) вынесены
   следующие генераторы мок-компонентов:
   * `mock_user_factory` — профиль авторизованного пользователя.
   * `mock_reminder_factory` — объект сущности напоминания.
   * `mock_objects_factory` — иерархическая структура Канбан-доски.
   * `mock_crud_factory` — перехватчик вызовов методов `BaseCRUD`.
3. **Форматирование:** Максимальная длина строки составляет **79 символов**,
   используются одинарные кавычки `'`, возвращаемые значения функций тестов
   явно аннотируются как `-> None`.
4. **Контекстные менеджеры:** При использовании `with pytest.raises`
   утверждения `assert` выносятся за пределы блока `with` во избежание
   появления недостижимого кода (`unreachable code`) при статическом анализе.

---

### 5. Подготовка окружения и инструкция по запуску

Перед первым запуском тестов необходимо создать локальные файлы настроек
из имеющихся шаблонов:

```bash
# Копирование шаблонов конфигурации для тестовых баз данных
cp tests/.env.flow.test.example tests/.env.flow.test
cp tests/.env.tasks.test.example tests/.env.tasks.test
```

Все команды автоматизированы и обернуты в системный `Makefile`:

```bash
# Запуск тестов для домена задач (Tasks)
make test-tasks

# Запуск тестов для домена процессов (Flow)
make test-flow

# Проверка проекта линтерами (Ruff) и статическая типизация (Mypy)
make check-all
```
